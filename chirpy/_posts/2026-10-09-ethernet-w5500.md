STM32에서 W5500을 사용할 때는 **MCU↔W5500의 SPI**와 **W5500↔네트워크의 Ethernet/TCP/IP**를 나눠 이해하면 편합니다. MCU는 SPI로 W5500의 레지스터·버퍼에 접근하고, W5500은 Ethernet MAC·PHY와 하드웨어 TCP/IP 기능을 제공합니다. 칩이 TCP와 UDP를 지원한다는 사실과 프로젝트에서 실제로 사용한 프로토콜은 구분해야 합니다. 이 프로젝트의 기록은 Ethernet을 통한 **TCP 경로**를 중심으로 합니다. [WIZnet W5500 제품 설명](https://docs.wiznet.io/Product/Chip/Ethernet/W5500)

```text
STM32 ── SPI ── W5500 ── Ethernet 케이블/스위치 ── PC
                     │
             MAC·PHY / IPv4 / TCP 소켓
```

## 1. SPI를 먼저 확인한다

네트워크 소켓이 열리지 않더라도 원인이 IP 설정이라고 단정하면 안 됩니다. 먼저 칩 선택·클록·MOSI·MISO·전원·리셋을 확인합니다. W5500 문서는 SPI Mode 0과 3을 지원한다고 설명합니다. SPI 헤더에는 주소와 블록 선택·읽기/쓰기 제어 정보가 포함됩니다. [W5500 데이터시트](https://docs.wiznet.io/img/products/w5500/W5500_ds_v110e.pdf)

통합 프로젝트의 코드 발췌에서는 버전 레지스터 `0x0039`를 한 바이트 읽도록 요청했습니다.

```c
spi2_result_t w5500_read_version(uint8_t *version, uint32_t timeout_us)
{
    return w5500_read(0U, 0x0039U, version, 1U, timeout_us);
}
```

버전 레지스터가 예상값으로 읽히면 적어도 해당 SPI 읽기 경로를 점검할 근거가 생깁니다. 이것만으로 Ethernet 링크나 TCP 통신까지 정상이라고 결론 낼 수는 없습니다.

## 2. 물리 링크와 네트워크 주소를 구분한다

Ethernet 링크가 올라오려면 케이블, 커넥터, 상대 포트와 PHY 동작을 확인해야 합니다. 이후 MAC 주소, IP 주소, 서브넷 마스크, 게이트웨이 등 네트워크 구성을 확인합니다. 같은 서브넷 PC와 통신할 때와 라우터를 거쳐야 할 때 필요한 조건이 다릅니다.

```text
SPI 레지스터 접근 → Ethernet 링크 → IP 설정 → TCP 소켓 → 응용 명령
```

각 단계가 성공해야 다음 단계를 의미 있게 볼 수 있습니다. 케이블 링크가 살아 있어도 IP가 틀리면 서버에 연결되지 않을 수 있고, TCP 연결이 열려도 명령 파서가 잘못되면 응답이 없을 수 있습니다.

## 3. TCP 소켓은 별도 설정이다

W5500은 하드웨어 소켓을 제공합니다. TCP 서버로 쓸 때는 소켓 모드와 포트 설정, 소켓 열기와 수신 대기 등 상태 전이를 관리해야 합니다. 기존 코드 노트에는 서버 포트 설정과 실패 시 중단하는 부분이 정리되어 있습니다. [WIZnet W5500 TCP 설명](https://docs.wiznet.io/Product/Chip/Ethernet/W5500/Application/tcp)

프로젝트의 명령 파서는 TCP 경로와 RS-485 경로를 번갈아 확인하고 요청이 온 경로로 응답하도록 구성됐습니다. 네트워크를 통한 메시지 처리 방식은 [TCP-IP](/posts/tcp-ip/)에서 이어집니다.

## 단계별로 문제를 찾는 순서

1. W5500 버전 레지스터가 안정적으로 읽히는지 확인합니다.
2. Ethernet 링크 상태를 확인합니다.
3. MAC·IP·서브넷·게이트웨이 설정과 PC 주소를 비교합니다.
4. 소켓 모드·포트·연결 상태를 확인합니다.
5. 연결 뒤 송수신 바이트와 응용 메시지 경계를 확인합니다.

이 글의 프로젝트 사례는 보관함에 정리된 코드와 경험을 바탕으로 합니다. 코드가 있는 기능과 실제 장비에서 확인된 동작 범위는 별도로 봅니다.
