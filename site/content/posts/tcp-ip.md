IP는 네트워크에서 장치 간 패킷을 전달하는 계층이고, TCP는 두 끝점 사이에서 **순서가 있는 신뢰성 있는 바이트 스트림**을 제공합니다. TCP는 손실을 탐지하고 재전송하지만, 앱이 만든 한 번의 `send`가 상대 앱의 한 번의 `recv`와 일대일로 대응한다고 보장하지 않습니다. [TCP 표준 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293)

## 주소와 포트

```text
서버: 192.168.0.10:5000  ← TCP 연결 ←  클라이언트
```

위 주소는 설명용 예시입니다. IP 주소는 네트워크의 장치를, 포트는 해당 장치에서 실행되는 서비스를 구분합니다. 서버는 지정 포트에서 연결을 기다리고 클라이언트가 접속합니다. STM32 통합 프로젝트는 W5500을 통한 TCP 연결과 PC 통신을 코드로 구성했으며, 별도의 로봇 운영 앱에서도 TCP로 장비 명령을 주고받았습니다.

## TCP의 전송 단위와 앱의 메시지 단위

TCP가 순서를 지켜 바이트를 전달하더라도, 응용 메시지의 경계는 앱이 정해야 합니다.

```text
송신: "PING\r\n" 한 번
수신 1: "PI"
수신 2: "NG\r\n"
```

반대로 메시지 두 개가 한 번에 들어올 수도 있습니다. 따라서 수신 데이터를 버퍼에 누적하고 줄바꿈, 길이 필드 또는 고정 길이 기준으로 완성된 메시지를 꺼냅니다. 이 예시는 TCP의 바이트 스트림 성질을 설명하는 것이며, 특정 호출이 항상 이런 식으로 분할된다는 뜻은 아닙니다. [RFC 9293의 세그먼트 설명](https://www.rfc-editor.org/rfc/rfc9293#section-3.7)

## 연결 성공과 작업 완료는 다르다

TCP 연결이 열렸다는 사실은 장치가 명령을 이해했거나 물리 동작을 완료했다는 뜻이 아닙니다. 일반적인 장비 제어에서는 연결 상태, 명령 송신 성공, 시작 응답, 동작 완료 응답, 최종 작업 종료를 각각 나눠 관리합니다.

로봇 운영 소프트웨어에서는 연결 오류가 나면 명령 전송을 보류하고 미완료 작업을 보존한 뒤, 재접속 및 서버 확인 메시지 이후 처리를 재개하는 흐름을 구현했습니다. STM32 통합 프로젝트에서는 TCP와 RS-485 명령 경로를 번갈아 확인하고, 요청이 들어온 경로로 응답하는 구조를 작성했습니다.

## 끊김을 다룰 때

1. 연결 오류·상대 종료·제한 시간 초과를 구분합니다.
2. 연결이 끊긴 동안 새 명령을 보낼지 보류할지 정합니다.
3. 응답을 받지 못한 명령의 실행 여부는 알 수 없을 수 있으므로, 재전송 규칙을 응용 계층에서 정합니다.
4. 다시 연결되면 상대 상태를 확인하고 남은 작업을 결정합니다.

TCP의 재전송 기능은 네트워크 바이트 전달을 위한 것입니다. 앱이 동일한 장비 명령을 다시 보내도 안전한지까지 판단해 주지는 않습니다.

## W5500을 쓰는 경우

STM32가 SPI로 W5500 레지스터와 버퍼에 접근하고, W5500은 Ethernet과 TCP 소켓을 처리합니다. 따라서 통신 문제가 생기면 **SPI → 링크 → IP → TCP → 응용 메시지** 순서로 범위를 좁힙니다. W5500이 UDP도 지원하지만, 이 글의 프로젝트 경험은 TCP 경로에 관한 것입니다. [WIZnet W5500 개요](https://docs.wiznet.io/Product/Chip/Ethernet/W5500)
